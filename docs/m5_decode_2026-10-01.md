# M5 one-token decode investigation (2026-10-01)

Base Apple M5, fanless, 24 GB; dense Qwen3.8-27B UD-Q3_K_XL, 64 GPU layers,
F16 KV. Baseline: `5f44309`. The agent prompt, tools, model quantization and
sampling parameters are not changed. No MTP or speculative generation is
enabled in this pass. Tests run sequentially under `caffeinate -disu`.

## TensorOps is not automatically a faster GEMV

The existing Metal 4 path already handles larger prefill batches. A dedicated
single-token IQ3_XXS TensorOps prototype used 16 output rows, K tiles of 256,
64 threads, FP32 operands and FP32 accumulators. With relaxed precision, its
5120 -> 17408 projection failed the existing tolerance (max 0.004236, RMS
0.0006174). With relaxed precision disabled, all quant/tail checks passed,
but the 17408 -> 5120 projection took 1.491 ms versus 0.488 ms for the baseline.
Four/eight K partitions passed the same checks after correcting partial-row
stores, but still took 1.442/1.442 ms. Those prototypes were removed.

This matches the important distinction in
[Apple's M5 talk](https://developer.apple.com/videos/play/tech-talks/111432/):
large GEMMs benefit from the matrix accelerators, while single-token decode
streams weights and is mainly constrained by memory. It is not evidence that
every possible one-token TensorOps implementation will be slower.

## Other trials and whole-model drift

- Four/eight output rows per SIMD improved some isolated IQ2 projections but
  did not establish a meaningful whole-model gain. `tg64`, five repetitions:
  eight rows 8.81 +/- 0.08, then baseline 8.76 +/- 0.06 tok/s.
- Keeping the IQ3_S FP32 lookup grid in a device buffer, rather than expanding
  it in each workgroup, passed CPU/tail checks but did not help: sampled
  generation measured 8.936 tok/s versus an earlier baseline 8.995.
- Fusing paired IQ3_S and SwiGLU passed CPU projection/tail checks, full CPU
  logits and the unchanged eight greedy IDs. Two synchronous isolated calls
  took 1.005 ms versus 0.783 for the fused call, but that includes an extra
  CPU/GPU round trip absent from ordinary batched model execution. A later
  paired full-model test gave only +0.07% forward throughput; discard it.
- Eight SIMD groups for every IQ2/IQ3_XXS format gave 8.75 +/- 0.14 tok/s in
  five-repeat `tg64`; the useful geometry is format-dependent.

Separate long series drifted substantially: selective IQ2 eight-group decode
gave 8.57 +/- 0.24, followed by baseline 7.90 +/- 0.25 tok/s. These numbers
must not be used to advertise a gain: time, temperature and scheduling are
confounders. All rejected kernels and switches were removed from production.

## Retained: amortize the larger IQ2 lookup tables

IQ2_XS/S use 4/8 KiB exact byte lookup caches. Sharing each cache across eight
SIMD groups (256 threads, 16 output rows), rather than two (64 threads, four
rows), reduces repeated initialization and cache allocation per output row.
Each SIMD group still computes the same two rows with the same FP32 operations
in the same order. IQ2_XXS and IQ3_XXS retain their old geometry. The policy is
automatic only on the measured base M5 and only for matrices with at least
4096 inputs and outputs. Small shapes and missing optional pipelines fall
back; `QW3_METAL_DENSE_IQ2_VECTOR=0` must retain its old-kernel meaning.

The diagnostic `tests/bench_decode_ab.m` uses two independent sessions with
the same prompt, history, seed and sampling settings. It alternates A/B and
B/A forward order per token, discards the first eight forwards from timing,
and checks both independently sampled token IDs at every step. Selection cost
is outside timing. The file includes the private Metal bridge so no mutable
test-control API is added to production. The two sessions have a different
cache footprint from a normal single-session run; absolute rates are not a
single-session performance claim.

| Paired run | Baseline | Selective IQ2 | Forward gain |
| --- | ---: | ---: | ---: |
| First | 8.861 tok/s | 8.907 tok/s | +0.48% |
| Repeat | 8.847 tok/s | 8.906 tok/s | +0.63% |
| Rebuilt retained policy | 8.868 tok/s | 8.926 tok/s | +0.63% |

All three runs produced the same 128-token hash `51138e1f4070fd90`, and all eight
timed blocks in each run favored the candidate. This is a small observed gain,
not the 20-30 tok/s previously estimated for a speculative architecture.
The rebuilt retained policy also produced that hash. Validation passed the
full dense bring-up (CPU projections/logits, greedy sequence, tails, F16/F32
KV, 128-token prefill/continuation and session roundtrip), MoE logit/greedy/
prefill regression, dense agent generation/checkpoint/prefix-cache smoke,
executor verification self-test and runtime fingerprint tests. Tolerances
were not relaxed. MTP is not involved in any of these measurements.
An additional bring-up run passed eight IQ2_XS/S large-matrix tail cases
(4352/5120 inputs, 4097/4111 outputs), exercising the eight-SIMD geometry
directly rather than only its small-shape fallback. External finite-value
and tolerance checks cover those cases as well.

After the later [text IMRoPE correction](text_imrope_2026-10-01.md), another
paired run gave 8.708/8.763 tok/s (+0.61% forward). Both variants produced
the same new 128-token hash `6e27f5726999f2da`. The different hash versus
earlier runs is due to the positional-rotation correctness fix, not the
IQ2 cache-sharing choice. A subsequent warm single-session sampled run
gave 8.503 tok/s (117.214 ms forward, 0.396 ms sampling); this is not an
interleaved before/after comparison or evidence of a large acceleration.

```sh
make qw3-decode-ab-bench
caffeinate -disu ./qw3-decode-ab-bench \
  ../../models/Qwen3.8-27B-UD-Q3_K_XL.gguf
make test-dense-metal-bringup test-metal-logits test-dense-agent
```

The subsequent MTP experiment was removed on 2026-10-03 after the local
benchmark failed to show a compelling generation benefit. Ordinary decode
and the text IMRoPE correction remain in the engine.
